# 银行家算法（Banker's Algorithm）完全讲解



## 一、从零开始：为什么需要银行家算法？

### 1.1 先理解"死锁"

假设操作系统里有两个进程 P0 和 P1，系统有两种资源：打印机和扫描仪，每种各一台。

```
时刻1：P0 拿到了打印机
时刻2：P1 拿到了扫描仪
时刻3：P0 还想要扫描仪 → 但扫描仪在 P1 手里，P0 只能等待
时刻4：P1 还想要打印机 → 但打印机在 P0 手里，P1 只能等待
```

结果：P0 等 P1 释放扫描仪，P1 等 P0 释放打印机。**谁也动不了，这就是死锁。**

### 1.2 银行家算法的思路

死锁很麻烦，那能不能**提前预防**？

银行家算法的思路是：**在分配资源之前，先"模拟"一下，看看分配之后系统会不会陷入死锁。如果会，就不分配；如果不会，才真正分配。**

就像一个谨慎的银行家：你来贷款，我先算一算——如果把钱借给你，剩下的钱够不够让其他客户都还完贷款？如果够，借；如果不够，拒绝。

## 二、用一个生活例子建立直觉

### 场景设定

你是一个银行家，手里有 **10 万块钱**。

你有 3 个客户：

| 客户 | 最多需要（Max） | 已经借走（Allocation） | 还需要（Need） |
|------|----------------|----------------------|----------------|
| 张三 | 8 万           | 3 万                 | 5 万           |
| 李四 | 4 万           | 2 万                 | 2 万           |
| 王五 | 6 万           | 1 万                 | 5 万           |

你手里还剩：10 - 3 - 2 - 1 = **4 万**（Available）

现在张三来说："我再借 2 万。" 你批不批？

### 银行家的思考过程

**第一步：先假装借给他**（预分配）

- 你手里变成：4 - 2 = 2 万
- 张三已借：3 + 2 = 5 万，还需要：5 - 2 = 3 万

**第二步：模拟一下，能不能找到一个顺序让大家都还完？**

先看现在谁能还完：
- 张三：还需要 3 万 > 你手里的 2 万 → 暂时不行
- 李四：还需要 2 万 ≤ 你手里的 2 万 → **可以！** 假装李四还完，你拿回他借的 2 万
- 现在你手里：2 + 2 = 4 万

再看：
- 张三：还需要 3 万 ≤ 4 万 → **可以！** 假装张三还完，你拿回 5 万
- 现在你手里：4 + 5 = 9 万

再看：
- 王五：还需要 5 万 ≤ 9 万 → **可以！** 王五也能还完。

**找到了一个顺序：李四 → 张三 → 王五**，所有人都能还完 → **安全！批准这笔贷款。**

### 如果找不到安全顺序呢？

假设王五来借 3 万。预分配后：
- 你手里：4 - 3 = 1 万
- 王五已借：1 + 3 = 4 万，还需要 2 万

模拟：
- 张三：需要 5 万 > 1 万 → 不行
- 李四：需要 2 万 > 1 万 → 不行
- 王五：需要 2 万 > 1 万 → 不行

**谁都动不了** → 不安全 → **拒绝这笔贷款，把预分配撤回。**

## 三、把生活例子翻译成术语

上面银行家的思考过程，就是算法的核心。把生活用语翻译成操作系统的术语：

```
银行家              →  操作系统
客户                →  进程（Process）
钱                  →  资源（Resource）
客户最多需要多少钱   →  Max（最大需求矩阵）
客户已经借了多少     →  Allocation（已分配矩阵）
客户还需要多少       →  Need（需求矩阵，Need = Max - Allocation）
银行家手里还剩多少   →  Available（可用资源向量）
假装借给他看看       →  预分配（试探性修改）
找到一个还钱顺序     →  安全序列（Safe Sequence）
```

## 四、代码中的数据结构（对应代码第 5~16 行）

理解了概念后，看看代码里是怎么存储这些信息的：

```
┌─────────────────────────────────────────────────────────────┐
│  进程数 M = 3，资源种类数 N = 3                               │
│                                                             │
│  Available[3]        →  系统当前可用的各资源数量                │
│                         例：[4, 4, 4] 表示 A资源4个,B资源4个... │
│                                                             │
│  Max[3][3]           →  每个进程最多需要多少资源                │
│                         Max[0] = [7, 5, 3] 表示P0最多需要7个A  │
│                                                             │
│  Allocation[3][3]    →  每个进程已经拿到多少资源                │
│                         Allocation[0] = [0, 1, 0]            │
│                                                             │
│  Need[3][3]          →  每个进程还需要多少资源                  │
│                         Need = Max - Allocation               │
│                         Need[0] = [7-0, 5-1, 3-0] = [7,4,3]  │
│                                                             │
│  Finish[3]           →  安全性检查用的标记数组                  │
│                         0 = 该进程还没被"模拟执行完"             │
│                         1 = 已经被"模拟执行完"                  │
│                                                             │
│  Work[3]             →  安全性检查时的"临时可用资源"             │
│                         一开始 = Available 的副本               │
│                         每当模拟一个进程执行完，就加上它归还的资源  │
│                                                             │
│  safe_arr[3]         →  记录安全序列的数组                     │
│                         存放进程的执行顺序，如 [1, 0, 2]        │
│                         表示 P1 → P0 → P2                     │
│                                                             │
│  State[3]            →  进程的真实执行状态                     │
│                         0 = Working（还在运行/等待）            │
│                         1 = Finished（已执行完毕，资源已归还）    │
└─────────────────────────────────────────────────────────────┘
```

**为什么要同时有 `Finish` 和 `State`？**

- `State` 记录的是进程**真实的状态**：这个进程真的跑完了，真的把资源还了。
- `Finish` 只在安全性检查时使用，是一个**临时标记**，检查完就作废了。它表示"如果我假装让这个进程跑完，它能不能跑完"。

两者不能混用，否则会互相干扰。

## 五、代码整体流程

用一句话概括：**读入数据 → 用户申请资源 → 合法性检查 → 预分配 → 安全性检查 → 安全就确认/不安全就回滚 → 循环。**

```
程序启动
  │
  ▼
init()：读入进程数、资源种类、Available、每个进程的 Max
  │
  ├─ Need 初始化为 Max（因为初始时没分配任何资源，所以还需要全部）
  │
  ├─ 第一次调用 handleRequest()（强制分配一次）
  │
  └─ 循环询问"是否继续申请？"
        │
        ├─ Y → 调用 handleRequest()
        └─ N → 打印最终状态表，退出
```

`handleRequest()` 内部：

```
handleRequest()
  │
  ├─ 1. 输入进程名，找到对应的下标
  ├─ 2. 输入该进程本次申请的资源数量 Request
  │
  ├─ 3. 合法性检查（第99~116行）
  │     ├─ Request > Available？→ 异常（你要的比系统有的还多）
  │     ├─ Request > Need？    → 异常（你要的比你总共需要的还多）
  │     └─ 都通过 → 继续
  │
  ├─ 4. 预分配（第118~123行）
  │     ├─ Available  -= Request
  │     ├─ Allocation += Request
  │     └─ Need       -= Request
  │
  ├─ 5. 安全性检查 checkSafe()（第125行）
  │     │
  │     ├─ 安全（返回 true）：
  │     │    ├─ 检查该进程的 Need 是否全部为 0
  │     │    │    ├─ 是 → 该进程执行完毕，释放它的全部资源
  │     │    │    │       Available += Allocation，Allocation 清零，State 标为 1
  │     │    │    └─ 否 → 什么都不做，预分配已经生效了
  │     │    └─ 打印安全序列，结束本次申请
  │     │
  │     └─ 不安全（返回 false）：
  │          ├─ 回滚：Available += Request，Allocation -= Request，Need += Request
  │          └─ 提示"无安全序列"，结束本次申请
  │
  └─ 6. 回到循环询问
```

## 六、逐段代码详解

### 6.1 初始化 init()（第 21~74 行）

```java
public void init() {
    // 读入进程数和资源种类数
    n = sc.nextInt();
    M = n;
    zy = sc.nextInt();
    N = zy;

    // 根据进程数和资源种类数，创建各个数组
    Available = new int[N];        // 长度 = 资源种类数
    Max = new int[M][N];           // 行 = 进程数，列 = 资源种类数
    Allocation = new int[M][N];    // 同上
    Need = new int[M][N];          // 同上
    // ... 其他辅助数组

    // 读入系统初始资源数量
    // 例：3 种资源，输入 "10 5 7" 表示 A 有 10 个，B 有 5 个，C 有 7 个
    for (int i = 0; i < N; i++) {
        Available[i] = sc.nextInt();
    }

    // 读入每个进程的最大需求
    // 例：输入 "P0 7 5 3" 表示 P0 最多需要 7 个 A、5 个 B、3 个 C
    for (int i = 0; i < M; i++) {
        Name[i] = sc.next();          // 进程名，如 "P0"
        for (int j = 0; j < N; j++) {
            Max[i][j] = sc.nextInt();  // 最大需求
            Need[i][j] = Max[i][j];    // ★ 关键：初始时 Need = Max
        }
    }
}
```

**为什么要初始化 Need = Max？**

因为程序刚开始运行时，系统还没有给任何进程分配资源。一个进程还没拿到任何资源，那它"还需要的"就等于"它最多需要的"。

随着后续分配，Need 会逐渐减小：`Need = Max - Allocation`

### 6.2 资源申请处理 handleRequest()（第 76~161 行）

这是整个程序最核心的函数。我把它拆成 3 个阶段讲解。

#### 阶段 A：输入与合法性检查（第 76~116 行）

```java
// 用户输入进程名，程序在数组中找到对应的下标
String targetName = sc.next();
int pIdx = -1;
for (int i = 0; i < M; i++) {
    if (Name[i].equals(targetName)) {
        pIdx = i;
        break;
    }
}

// 用户输入该进程本次申请的资源数量
for (int j = 0; j < N; j++) {
    Request[pIdx][j] = sc.nextInt();
}

// 合法性检查
for (int j = 0; j < N; j++) {
    if (Request[pIdx][j] > Available[j]     // 条件1：申请的 > 系统可用的
        || Request[pIdx][j] > Need[pIdx][j]) // 条件2：申请的 > 还需要的
    {
        isAbnormal = true;
        break;
    }
}
```

**两个检查条件的含义：**

- **Request > Available**：你管系统借 5 个打印机，但系统只有 3 个，这不可能满足。直接拒绝。
- **Request > Need**：你最多需要 5 个打印机（Max），已经拿到了 3 个（Allocation），那你最多还需要 2 个（Need）。你来申请 4 个？这不合理，说明输入有误，拒绝。

#### 阶段 B：预分配（第 118~123 行）

```java
Available[j] -= Request[pIdx][j];       // 系统可用的减少
Allocation[pIdx][j] += Request[pIdx][j]; // 进程已分配的增加
Need[pIdx][j] -= Request[pIdx][j];       // 进程还需要的减少
```

**为什么要"预分配"而不是直接分配？**

因为此时我们还不知道分配后系统是否安全。如果直接分配，发现不安全后再撤回，万一撤回过程中出错就很麻烦。

所以代码的设计思路是：**先用临时修改来"试探"，安全了就保留，不安全就撤回。**

这三行代码就是"假装给你了"。接下来看看给完之后系统是不是安全的。

#### 阶段 C：安全性检查 + 最终决策（第 125~159 行）

```java
if (checkSafe()) {
    // ---- 安全：确认分配 ----

    // 检查这个进程是否已经拿满了所有它需要的资源
    boolean finished = true;
    for (int j = 0; j < N; j++) {
        if (Need[pIdx][j] != 0) finished = false;
    }

    if (finished) {
        // 进程执行完毕，释放它占有的全部资源
        State[pIdx] = 1;  // 标记为已完成
        for (int j = 0; j < N; j++) {
            Available[j] += Allocation[pIdx][j]; // 资源归还给系统
            Allocation[pIdx][j] = 0;             // 清空已分配记录
        }
    }
    // 如果没拿满，什么都不做——预分配已经修改了三个数组，这就是最终状态

} else {
    // ---- 不安全：回滚 ----
    // 把预分配的三行操作全部反过来
    Available[j] += Request[pIdx][j];       // 系统可用的加回来
    Allocation[pIdx][j] -= Request[pIdx][j]; // 进程已分配的减回去
    Need[pIdx][j] += Request[pIdx][j];       // 进程还需要的加回来
}
```

**进程完成时为什么要释放资源？**

一个进程拿到了它需要的全部资源后，就会执行完毕。执行完毕后，它占有的所有资源都要归还给系统。就像客户还清了贷款，银行家手里又多了钱，可以贷给其他客户。

**回滚代码为什么是预分配的"逆操作"？**

预分配做了什么：
```
Available  减去 Request
Allocation 加上 Request
Need       减去 Request
```

回滚就是把这三步反过来：
```
Available  加上 Request（抵消之前的减）
Allocation 减去 Request（抵消之前的加）
Need       加上 Request（抵消之前的减）
```

### 6.3 安全性检查 checkSafe()（第 163~196 行）

**这是整个算法的灵魂。** 它回答的问题是：在当前资源状态下，能不能找到一个顺序，让所有还没完成的进程都执行完毕？

#### 算法思路（用人话说）

假设你是银行家，手里有 Work 万块钱（一开始等于 Available）。

1. 把所有客户标记为"还没还完"（Finish = 0）
2. 循环以下步骤：
   - 找一个"还没还完"且"需要的钱 ≤ 你手里的钱"的客户
   - 如果找到了：假装他还完了，你拿回他借的所有钱（Work += Allocation），标记他为"已还完"
   - 如果找不到任何一个满足条件的客户：**不安全！** 有人永远还不完。
3. 如果所有客户都标记为"已还完"：**安全！**

#### 代码逐行对应

```java
private boolean checkSafe() {
    // 第1步：Work = Available 的副本
    // 为什么要复制？因为 Available 是系统的真实数据，不能被检查过程污染
    for (int i = 0; i < N; i++)
        Work[i] = Available[i];

    // 第2步：初始化 Finish 数组
    // 已经完成的进程（State=1）直接标记为 Finish=1，不需要再检查
    // 未完成的进程标记为 Finish=0
    for (int i = 0; i < M; i++)
        Finish[i] = State[i];

    // 统计有多少个进程还没完成，作为循环终止条件
    int target = 0;
    for (int i = 0; i < M; i++)
        if (State[i] == 0) target++;

    // 第3步：核心循环——最多需要找到 target 个进程
    int foundIdx = 0;
    while (foundIdx < target) {
        boolean found = false;  // 本轮是否找到了可执行的进程

        // 遍历所有进程
        for (int i = 0; i < M; i++) {
            if (Finish[i] == 0) {  // 条件A：还没被标记为完成

                // 条件B：检查 Need[i] 的每个分量是否都 ≤ Work 的对应分量
                boolean canAlloc = true;
                for (int j = 0; j < N; j++) {
                    if (Need[i][j] > Work[j]) {
                        canAlloc = false;
                        break;
                    }
                }

                if (canAlloc) {
                    // ★ 找到了！假装这个进程执行完毕，归还资源
                    for (int j = 0; j < N; j++)
                        Work[j] += Allocation[i][j];
                    Finish[i] = 1;              // 标记为完成
                    safe_arr[foundIdx++] = i;    // 记录到安全序列
                    found = true;
                }
            }
        }

        // 本轮扫描完，没有找到任何可执行的进程 → 不安全
        if (!found) return false;
    }

    // 所有未完成的进程都找到了 → 安全
    return true;
}
```

#### 用一个完整的例子走一遍安全性检查

**设定：3 个进程，3 种资源（A, B, C）**

```
系统初始资源 Available = [10, 5, 7]

        Max          Allocation     Need(=Max-Allocation)
P0    [7,  5,  3]    [0,  1,  0]    [7,  4,  3]
P1    [3,  2,  2]    [2,  0,  0]    [1,  2,  2]
P2    [9,  0,  2]    [3,  0,  2]    [6,  0,  0]

当前 Available = 10-0-2-3 = [5, 4, 5]
```

**安全性检查过程：**

```
初始：Work = [5, 4, 5]，Finish = [0, 0, 0]

第 1 轮扫描：
  P0: Need=[7,4,3] vs Work=[5,4,5] → 7 > 5 ❌ 不行
  P1: Need=[1,2,2] vs Work=[5,4,5] → 1≤5, 2≤4, 2≤5 ✅ 行！
      → 假装 P1 执行完，归还资源
      → Work = [5,4,5] + [2,0,0] = [7, 4, 5]
      → Finish = [0, 1, 0]
      → safe_arr = [1]（记录下标）

第 2 轮扫描：
  P0: Need=[7,4,3] vs Work=[7,4,5] → 7≤7, 4≤4, 3≤5 ✅ 行！
      → 假装 P0 执行完，归还资源
      → Work = [7,4,5] + [0,1,0] = [7, 5, 5]
      → Finish = [1, 1, 0]
      → safe_arr = [1, 0]

第 3 轮扫描：
  P2: Need=[6,0,0] vs Work=[7,5,5] → 6≤7, 0≤5, 0≤5 ✅ 行！
      → 假装 P2 执行完，归还资源
      → Work = [7,5,5] + [3,0,2] = [10, 5, 7]
      → Finish = [1, 1, 1]
      → safe_arr = [1, 0, 2]

所有进程都完成 → 安全！
安全序列为：P1 → P0 → P2
```

**为什么安全序列可能不唯一？**

在上面第 1 轮中，如果先选 P2 而不是 P1（P2 的 Need=[6,0,0] vs Work=[5,4,5] → 6>5 不行，所以这个例子里不行）。

换一个例子：如果 Available = [10, 5, 7]，P2 的 Need=[4,0,0]，那么 P1 和 P2 在第 1 轮都能被选中，选哪个都行，就会得到不同的安全序列。**只要能找到任意一个安全序列，系统就是安全的。**

### 第一次申请：P1 申请 (1, 0, 2)

合法性检查：Request=[1,0,2]
  1 ≤ Available[0]=5 ✅

      → Work = [10,4,7] + [0,1,0] = [10, 5, 7]

## 八、关键设计思想总结

### 8.1 "先试探，再确认"模式

这是银行家算法最核心的设计模式：

```
预分配（修改数据） → 安全性检查 → 安全就保留 / 不安全就回滚
```

这种模式在很多算法中都有出现，比如数据库的事务回滚、游戏中的"悔棋"功能。本质是：**先做假设，验证假设，假设成立就采纳，不成立就撤销。**

### 8.2 "模拟执行"的思想

安全性检查并不真的让进程执行，而是"假装"它执行完了，看看资源够不够让下一个进程也执行完。这种"模拟"思想在算法中很常见。

### 8.3 为什么安全性检查要循环扫描？

因为资源是**连锁释放**的：P1 执行完后释放的资源，可能刚好够 P0 用。所以不能只看一轮，要反复扫描，每找到一个就更新 Work，直到某轮一个都找不到为止。

## 九、常见疑问解答

**Q：为什么不直接分配，发现死锁了再处理？**

A：死锁一旦发生，处理代价很高（可能要强制杀掉进程、丢失数据）。银行家算法的思路是"预防"——在死锁发生之前就避免它。

**Q：安全性检查的时间复杂度是多少？**

A：O(M² × N)。外层 while 最多循环 M 轮（每轮至少找到一个进程），每轮内部遍历 M 个进程，每个进程比较 N 种资源。

**Q：Work 和 Available 为什么要分开？**

A：Available 是系统的**真实数据**，不能被安全性检查修改。检查过程需要"假设性地"改变可用资源量（每假装一个进程执行完，Work 就要加上它归还的资源），所以用一个副本 Work 来做这些假设操作。

**Q：为什么回滚代码是预分配的逆操作？**

A：因为预分配修改了三个数组（Available、Allocation、Need），回滚就是把每个数组的修改**原样撤回**。Available 减了多少就加回来，Allocation 加了多少就减回去，Need 减了多少就加回来。

**Q：State 和 Finish 的区别？**

A：`State` 记录进程**真实**的完成状态——它真的执行完了、资源真的归还了。`Finish` 是安全性检查中的**临时标记**——"如果这个进程能执行完就标记为 1"，检查结束后 Finish 的值就没有意义了。两者不能混用，否则安全性检查会污染真实状态。

**Q：这个算法有什么局限性？**

A：
1. 需要提前知道每个进程的 Max（最大需求），但实际中进程可能不知道自己最多需要多少。
2. 进程数和资源种类数是固定的，不能动态变化。
3. 算法假设进程会"配合"——拿到资源后最终会归还，但现实中进程可能崩溃。
4. 安全性检查本身有开销，频繁申请资源时会影响性能。
