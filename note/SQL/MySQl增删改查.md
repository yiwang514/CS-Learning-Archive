# MySQL 增删改查核心笔记

---

## 一、DDL 三大基本命令与 ALTER TABLE

**需要用到 `ALTER` 的情况：** 任何改变表的"骨架"的操作都必须用 `ALTER TABLE`。

DDL 分为三个基本命令：

| 命令 | 作用 |
|------|------|
| `CREATE TABLE` | 创建表 |
| `ALTER TABLE` | 修改表结构 |
| `DROP TABLE` | 删除表 |

---

## 二、数据类型细节：VARCHAR 与 BIGINT

- **`VARCHAR`** 表示"**可变长度字符串**"（**V**ariable **Char**acter），用于存储文本数据。括号里的数字（如 `VARCHAR(11)`）表示该字段允许存储的**最大字符数**（不是字节数）。

- **`BIGINT(20)`** 括号里的 `20` **不是**能存 20 位数，也**不是**占 20 个字节——它仅仅是一个**"显示宽度"（Display Width）**。它对数据的实际存储范围和占用的磁盘空间**没有任何影响**。

## 三、LIKE 模糊匹配速查

```sql
WHERE name LIKE "%V%"   -- 包含 "V"
WHERE name LIKE "%V"    -- 以 "V" 结尾
WHERE name LIKE "V%"    -- 以 "V" 开头
```

## 四、WHERE vs HAVING —— 核心辨析

> **`WHERE`** 是入学面试，负责在数据**分组前**筛选掉不合格的单条记录（**个体**）；
> **`HAVING`** 是分班之后的"优秀班级"评比，负责在**分组后**筛选掉不合格的分组数据（**集体**）。

### SQL 内部执行顺序

数据库在执行一条 SQL 时，并不是从左到右读的，它的内部执行顺序通常是：

| 步骤 | 子句 | 说明 |
|:---:|------|------|
| 1 | `FROM` | 先找到哪张表 |
| 2 | `WHERE` | 过滤掉不符合条件的原始行 — ❌ **此时聚合函数还没开始计算呢！** |
| 3 | `GROUP BY` | 把剩下的数据分组 |
| 4 | `HAVING` | 对分组后的数据进行过滤 — ✅ 聚合函数在这里生效 |
| 5 | `SELECT` | 决定展示哪些列 — ✅ 聚合函数在这里生效 |
| 6 | `DISTINCT` | 对结果去重 |
| 7 | `ORDER BY` | 最后排序 |
| 8 | `LIMIT` | 分页截取 |

> ⚠️ **经典错误：** `WHERE price > AVG(price)`
>
> 因为 `WHERE` 执行得太早了，这时候数据库根本还不知道平均分（`AVG`）是多少，所以它没办法在 `WHERE` 后面用聚合函数。

## 五、为什么 SELECT 必须放最前面？

**Q：为啥 `SELECT` 一定得放最前面？聚合函数为啥不能放 `FROM 表名` 的后面？**

**A：** 计算机比人类要笨得多。当你把一条 SQL 语句发送给数据库时，数据库里有一个叫 **"SQL 解析器（Parser）"** 的组件，它就像一个极其严格的**"语法检查官"**。这个检查官手里有一张**"死表"（语法蓝图）**，规定了 SQL 查询必须以特定的关键词开头。

如果你写成：
```sql
AVG(score) SELECT * FROM stu;
```
解析器刚读到第一个词 `AVG`，当场就死机了。因为它不知道你接下来要干嘛：
- 你是要搞查询（`SELECT`）？
- 还是要在别人的表里删数据（`DELETE`）？
- 还是想修改数据（`UPDATE`）？

**开头的第一个词（如 `SELECT`），是整句话的"大方向宣告"。** 没有这个宣告，数据库连接下来该启用哪套处理引擎都不知道。所以，聚合函数**绝对不能抢跑在 `SELECT` 前面**。

### ❌ 为什么不能放在 `FROM stu` 的后面？

如果你写成：
```sql
SELECT FROM stu AVG(score);
```
解析器读到 `FROM stu` 的时候，在它的"大脑预设"里，`FROM` 后面只能跟着**数据源**（表名、视图或者联表条件）。`FROM stu` 的意思是"定位到学生表"。如果后面紧接着蹦出一个 `AVG(score)`，解析器会认为这是一个错误的表名，或者是一个语法垃圾，从而直接报错拒绝。这就好比你在填写家庭住址时，写完"北京市海淀区"，后面突然紧接着写了一个"加法计算器"，系统当然无法识别。

> 📝 **书写顺序（`SELECT ... FROM ... WHERE ...`）** 是人类在上世纪 70 年代设计 SQL 时，写给人类自己看的**"人机契约"**。它模仿了英语的祈使句结构——*Select vegetables from the fridge（从冰箱里挑选蔬菜）*。

## 六、FROM 表名后面能接什么？

**Q：那什么能放在表名的后面呢？**

**A：** 在 SQL 的世界里，`FROM 表名` 的意思是"**找到了数据源**"。既然你已经站在了仓库（表）的大门口，接下来你能做的动作，必须符合"处理原料"的正常逻辑。

通常情况下，表名后面能直接接的关键词主要有以下**四大类**：

### 1. 过滤原料的词：`WHERE`
这是最常见的情况。你刚走进仓库，第一件事往往就是把不合格的原料扔掉。

```sql
FROM stu WHERE age > 18
```
> 逻辑：找到了学生表（`stu`），紧接着把年龄大于 18 岁的人筛选出来。

### 2. 跨库联合的词：`JOIN`（以及 `ON`）
如果一个仓库的原料不够，你需要把隔壁仓库的原料调过来一起用，这就是"连表查询"。

```sql
FROM stu JOIN class ON stu.class_id = class.id
```
> 逻辑：找到了学生表（`stu`），紧接着联合（`JOIN`）班级表（`class`），并规定联合的绑定条件（`ON`）。

### 3. 起小名的词：`AS`（或者直接空格）
有时候表名太长（比如 `student_score_information_table`），写起来太累，你可以在表名后面直接给它起个简短的代号（别名）。

```sql
FROM student_score_table AS s
-- 或者
FROM student_score_table s
```
> 逻辑：找到了这张长表，紧接着规定以后在语句里用字母 `s` 来代表它。

### 4. 流程推进的词：`GROUP BY` / `ORDER BY` / `LIMIT`
如果你的数据不需要过滤（不用 `WHERE`），也不需要连表（不用 `JOIN`），那么传送带就会直接进入下一步流程：

```sql
FROM stu GROUP BY gender          -- 直接把表里所有数据拿去分堆
FROM stu ORDER BY score DESC      -- 直接把表里所有数据拿去排序
FROM stu LIMIT 10                 -- 直接限制拿取的数据行数（只拿前 10 行）
```

## 七、SQL 执行顺序全景（奶茶店比喻）

| 物理执行顺序 | 关键字 | 奶茶店的现实角色 | 它的作用本质 |
|:---:|----------|:--------------:|--------------|
| 1 | `FROM` | 仓库大门 | 定位数据源（把账单本搬出来） |
| 2 | `WHERE` | 门卫大爷 | 对原始单行数据进行初筛（扔掉废票） |
| 3 | `GROUP BY` | 包装员工 | 将散落的单据按种类分堆（把个体压缩成群体） |
| 4 | `HAVING` | 质检经理 | 对分好的堆进行称重和筛选（扔掉不合格的整堆） |
| 5 | `SELECT` | 提取员 | 提取你想要的最终列，并给它们贴上小名 |
| 6 | `ORDER BY` | 排版秘书 | 拿到提取好的小巧报告，按高低顺序重新排列 |
| 7 | `LIMIT` | 剪刀手 | 根据老板要求，一刀切下需要的行数（比如前 3 名） |

### 对应的终极书写规则（必须严格遵守这个先后顺序）

```sql
SELECT ...
FROM ...
WHERE ...
GROUP BY ...
HAVING ...
ORDER BY ...
LIMIT ...;
```

## 八、主键（Primary Key）

**主键（Primary Key）** 是数据表中的一列（或多列的组合），其值能够**唯一地标识表中的每一行数据**。

> 这句干巴巴的课本定义，其实就是在描述"学号"的作用。在数据库里，主键就是这行数据的**"身份证号"**或**"绝对坐标"**。

### 主键的两大核心强制规则

为了能承担起"绝对坐标"的重任，数据库系统在底层给主键强加了两个**必须同时满足**的物理约束：

| 约束 | 说明 |
|------|------|
| **唯一性约束（Unique）** | 这一列里的任何两个值绝对不能相同。（对应学号绝不重复）如果数据库里已经有一行数据的主键是 `1`，你再试图插入一行主键为 `1` 的数据，数据库会直接报错并拒绝你。 |
| **非空约束（Not Null）** | 这一列的值绝对不能是空白的。（对应不能没有学号）你不能往数据库里塞一个没有"身份证"的黑户数据。 |

### 主键三铁律

1. **必须有：** 每张表必须有且只有一个主键。
2. **用数字：** 尽量用无意义的、数据库自动生成的自增整数（`ID`）当主键，别用业务字段（姓名、手机号）。
3. **不要动：** 数据一旦写进去，天王老子来了也不能修改它的主键。

## 九、ALTER TABLE 操作速查：ADD / MODIFY / CHANGE

**Q：咋同一个 `ALTER TABLE` 语句后面，一会儿跟 `ADD`，一会儿跟 `MODIFY`，如何区分啊？**

### 1. `ADD` —— 只管"生孩子"
只要是**原来没有、现在要加**的东西，一律用 `ADD`。

### 2. `MODIFY` —— MySQL 里的"整容手术"
当你要改变一个**已有字段**的类型、长度、是否为空时，MySQL 用 `MODIFY COLUMN`（或者直接 `MODIFY`）。

> ⚠️ **`MODIFY` 的坑：** 你必须把**完整的列定义重新写一遍**！不能只写"我要改长度"，得连类型、约束、注释一起重写。漏写了 `NOT NULL`，原来有的 `NOT NULL` 就丢了。

### 3. `CHANGE` —— MySQL 特有的"改名 + 整容二合一"
如果你不仅要改字段定义，还要改**字段名**，MySQL 必须用 `CHANGE`（而且**新名字和旧名字都要写**）。

### 4. `ALTER COLUMN ... SET DEFAULT` —— 只动默认值（轻量级）
MySQL 里还有一种更轻量的写法，专门用来改默认值，不改类型、不加锁重建表。

### 速查决策树

```
我要干什么？
│
├── 加新字段 / 加约束 / 加索引？
│   └──> ALTER TABLE 表名 ADD ...
│
├── 改已有字段的类型 / 长度 / NOT NULL？
│   └──> ALTER TABLE 表名 MODIFY COLUMN ...          （MySQL）
│       ALTER TABLE 表名 ALTER COLUMN ...            （其他库）
│
├── 改字段名？
│   └──> ALTER TABLE 表名 CHANGE 旧名 新名 类型...    （MySQL）
│
├── 只改默认值？
│   └──> ALTER TABLE 表名 ALTER COLUMN 字段 SET DEFAULT ...
│
└── 删字段 / 删约束 / 删索引？
    └──> ALTER TABLE 表名 DROP ...
```
