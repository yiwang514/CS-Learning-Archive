**第一节变量**

在实际的数据库运维和开发中，因为“系统变量”的作用范围差异巨大，所以大家通常会把系统变量一分为二：**全局变量** 和 **会话变量**。

这样一来，就凑齐了你看到的“四大变量家族”：

1. **全局变量（Global Variables）** ── 属于系统变量
2. **会话变量（Session Variables）** ── 属于系统变量
3. **用户变量（User Variables）** ── 开发者自定义（带 `@`）
4. **局部变量（Local Variables）** ── 代码块内部专属（`DECLARE`）

我们继续运用“从具体到抽象”**的方法，把这四种变量放在**“连锁奶茶店”的场景里，你就能秒懂它们各自的地位和脾气。

## 第一阶段：感性认识（连锁奶茶店的四个“记事本”）

假设你现在是“连锁奶茶店”的总工程师，负责给所有门店的收银机电脑设计系统。

### 1. 全局变量（Global）：【总公司的全国统一规章】

* **现实场景**：总公司规定，全中国所有的分店、所有的收银机，默认的“自动退单超时时间”统一为 **30 分钟**。
* **特点**：只要你在总公司后台改了这个数字，全全国所有正在开机的、未来要开机的电脑，**全部生效**。它影响的是“整个数据库服务器”。

### 2. 会话变量（Session）：【某个分店收银机的当班设置】

* **现实场景**：今天北京分店的网速极慢，店长觉得 30 秒超时太短了，于是他在**自己这台收银机**上临时修改：“我这台电脑的超时时间改为 **60 秒**”。
* **特点**：这只影响他**眼前这台电脑**（当前的连接/会话）。别的分店电脑依然是 30 秒；而且等他晚上关机重启，这台电脑又会恢复成总公司的默认值。

### 3. 用户变量（User）：【收银员自己贴的“便利贴”】

* **现实场景**：收银员小明在算账，随手在屏幕旁贴了张便利贴 `@temp_price = 100`。
* **特点**：带有 **`@`** 符号。这个便利贴是小明私人建立的，只在小明登录的这几个小时里有用。小明下班注销账号，便利贴就被保洁阿姨撕掉扔了。

### 4. 局部变量（Local）：【打印小票程序里的“临时计算草稿纸”】

* **现实场景**：收银机内部有一段自动打折的代码，在计算“满100减20”的瞬间，代码内部产生了一个临时的草稿纸 `discount = 20`。
* **特点**：用 **`DECLARE`** 声明。只在这一段特定的计算代码（存储过程/函数）运行的那几毫秒里存在，小票打印完的瞬间，草稿纸就灰飞烟灭了。

## 第三阶段：深入语法与实战细节

为了让你在看别人写的复杂 SQL 时不再迷路，我们把这四种变量的代码形态一一拆解：

### 1. 全局变量 (Global System Variables)

这是数据库管理员（DBA）最常调整的东西，比如修改数据库的最大连接数、时区、缓存大小。

```sql
-- 查看数据库当前的全局时区设置
SELECT @@global.time_zone;

-- 修改全局最大连接数为 1000（影响后续所有连接）
SET GLOBAL max_connections = 1000;

```

### 2. 会话变量 (Session System Variables)

当你连接上数据库时，数据库会把全局变量**复制一份**给你作为你的“会话变量”。你在自己窗口里改会话变量，不会影响别人。

```sql
-- 查看我当前这个窗口的自动提交设置
SELECT @@session.autocommit;

-- 临时关闭我这个窗口的自动提交（不影响其他正在工作的同事）
SET SESSION autocommit = 0;
-- 简写（省略 SESSION，默认就是改会话）：
SET @@autocommit = 0;

```

### 3. 用户变量 (User-defined Variables)

这是你在写日常 SQL 查询脚本时**最常用**的临时存储工具。不需要提前指定数据类型，直接带 `@` 就能用。

```sql
-- 定义一个用户变量，把全校最高分存进去
SET @top_score = (SELECT MAX(score) FROM students);

-- 随时调用这个便利贴
SELECT * FROM students WHERE score = @top_score;

```

### 4. 局部变量 (Local Variables)

它只能写在数据库的存储过程（Stored Procedure）**或者**函数（Function）的内部，用来做复杂的自动化逻辑计算。必须先定义数据类型，才能使用。

```sql
DELIMITER //
CREATE PROCEDURE calculate_tax()
BEGIN
    -- 1. 必须在开头用 DECLARE 声明局部变量（无前缀，必须指定类型）
    DECLARE total_sales DECIMAL(10,2);
    DECLARE tax_rate DECIMAL(4,2) DEFAULT 0.05;
    
    -- 2. 给局部变量赋值
    SELECT SUM(price) INTO total_sales FROM orders;
    
    -- 3. 使用局部变量计算
    SELECT total_sales * tax_rate AS final_tax;
END //
DELIMITER ;

```

## 💡 快速记忆符号秘籍

以后你在代码里看到变量，只需要**看它的“前缀”**，就能瞬间判断它的身份：

1. **没有 `@` 符号，且开头写着 `DECLARE**` $\rightarrow$ **局部变量**（草稿纸，只活在代码块里）。
2. **只有一个 `@` 符号（如 `@my_var`）** $\rightarrow$ **用户变量**（便利贴，跟你这个连接同寿命）。
3. **有两个 `@@` 符号（如 `@@global.xxx` 或 `@@session.xxx`）** $\rightarrow$ **系统变量**（数据库的控制开关）。
* 带 `global` 是影响大家的**全局变量**。
* 带 `session`（或什么都不带）是只影响你自己的**会话变量**。



2.  变量小细节：
     SELECT @@GLOBAL.xxx 是去数据库“金库”里直接拿原始数据，拿出来的是底层存储的真实值（0 和 1）；
     SHOW GLOBAL VARIABLES 是经过 MySQL“前台接待”包装过的展示界面，把 0/1 翻译成了人类爱看的 ON/OFF。




3.  Q：为啥用SELECT赋值时只能用“：=”来赋值？
    A：这个问题问得极具穿透力！你敏锐地察觉到了 SQL 语法设计中一个非常经典、但也最容易让初学者抓狂的“双标”现象。

为什么 `SET @a = 1` 可以，而 `SELECT @a = 1` 就不行，非得写成 `SELECT @a := 1` 呢？

我们继续用“透过现象看本质”的方法，深入到**数据库解析器（SQL Parser）的大脑**里，看看它为什么会在这里产生“逻辑精神分裂”。

## 第一阶段：感性认识（现实生活中的“一词多义”歧义）

想象一下，你用中文对一个并不聪明的机器人助理说了一句话：

> **“小明是 18 岁。”**

这句话在人类语言里，其实潜藏着**两种完全不同的物理动作**：

1. **赋值（命令）**：“去，把小明的档案拿出来，把他的年龄**修改/设置**为 18 岁。”
2. **比较（提问）**：“你去查一下，小明现在的年龄**等于** 18 岁吗？”（机器人的回答应该是“是”或“不是”）。

你看，同一个“是”（对应数学符号 `=`），因为语境的不同，产生了歧义。为了不让机器人发疯，你必须用更精准的词汇来限定你的意图。

---

## 第二阶段：理性认识（抽象为数据库的“符号歧义”）

在 SQL 语言的底层设计中，等号 **`=`** 天生就是一个“比较运算符”（相当于 Python 或 Java 里的 `==`）。它的第一天职，是用来判断左右两边相不相等。

我们来看看数据库解析器在不同语境下，是如何理解 `=` 的：

### 1. 为什么在 `SET` 后面可以用 `=`？（有明确语境）

当你写下：

```sql
SET @age = 18;

```

数据库解析器读到第一个词 **`SET`（设置）** 的时候，它的大脑就进入了“赋值模式”。它知道你接下来要干嘛，所以当它看到后面的 `=` 时，它能百分之百确定：这里的 `=` 不是在提问，而是在下达**赋值**命令。所以它顺理成章地把 18 存进了 `@age`。

### 2. 为什么在 `SELECT` 后面用 `=` 会引发灾难？（语境错乱）

当你写下：

```sql
SELECT @age = 18;

```

解析器读到第一个词 **`SELECT`（查询/提取）** 时，它的大脑进入的是“提问模式”。
此时，它看到后面的 `@age = 18`，它会本能地把它当成一个**判断题**：

> *“主人是在问我，变量 `@age` 里面的值，是不是等于 18 呀？”*

于是，数据库会在底层做这样的运算：

* 如果 `@age` 之前刚好被存过 18，数据库会在屏幕上输出 **`1`（代表 True / 正确）**。
* 如果 `@age` 是空的或者存的是别的数字，数据库会在屏幕上输出 **`0`（代表 False / 错误）**。

**结论：在 `SELECT` 语句中，如果你写 `=`，数据库根本没有为你“赋值”，它只是在默默地做了一道“判断题”，然后把判断结果（0 或 1）告诉了你。**

## 第三阶段：深入本质（拯救歧义的专属符号 `:=`）

为了解决 `SELECT` 语句中这个极其致命的歧义，数据库的设计者们不得不引入一个新的符号来强行破局。

他们借鉴了早期编程语言（如 Pascal）中的语法，把冒号和等号拼在了一起：**`:=`**。

这个符号在数据库里拥有唯一的、绝对的物理含义：**纯粹的赋值运算**。
它身上没有任何“判断/比较”的基因。

当你写下：

```sql
SELECT @age := 18;

```

数据库解析器看到 `:=` 的瞬间，所有的歧义都烟消云散了。它立刻明白：

> *“不管我在什么模式下，只要看到 `:=`，主人的意思就是绝对的死命令——**把右边的 18 强行塞进左边的 `@age` 里，并且把这个 18 展示出来！***”

---

### 💡 终极防坑总结图

为了让你的肌肉产生永久记忆，请看这组核心对比：

| SQL 语句 | 数据库的内心 OS (如何理解？) | 实际发生的结果 | 屏幕展示的值 |
| --- | --- | --- | --- |
| `SET @a = 1;` | “有 SET 罩着，我知道这是让我把 1 存进 `@a`。” | **成功赋值** | (无展示，默默执行) |
| `SELECT @a = 1;` | “SELECT 模式下遇到 `=`，这是在问我 `@a` 等不等于 1。” | **根本没有赋值！只做了判断。** | `0` 或 `1` (True/False) |
| `SELECT @a := 1;` | “遇到 `:=` 死命令，立刻把 1 存进 `@a`，然后输出。” | **成功赋值** | `1` (你赋进去的值) |

这就是为什么在高级的 SQL 脚本里，只要你想在 `SELECT` 查询的过程中“顺手”抓取数据存入变量，就必须、也只能使用 `:=` 的根本原因。

假设你开了一家大型餐厅，你（前端程序员）在前面做服务员，数据库（MySQL）是后厨。

## 第二阶段：理性认识（抽象为课本定义与代码）

我们将生活场景翻译成数据库语言。

**课本定义：**

> **存储过程（Stored Procedure）**是一组为了完成特定功能的 SQL 语句集合。它经过编译后**直接存储在数据库服务器内部**。用户只需要通过指定存储过程的名字，就可以呼叫并自动执行这整套逻辑。

### 💡 工业级代码演示：如何写一份“后厨 SOP”

假设我们要写一个打折结算的存储过程。你会发现，上一节学的局部变量（DECLARE）在这里大显身手了：

```sql
-- 1. 告诉数据库：先把语句结束符由分号 ; 改为 //，防止写到一半数据库以为写完了
DELIMITER //

-- 2. 开始写 SOP（创建存储过程）
CREATE PROCEDURE `自动结算打折订单`()
BEGIN
    -- 3. 拿出局部变量（草稿纸）
    DECLARE total_price DECIMAL(10,2);
    
    -- 4. 第一步：算总价
    SELECT SUM(price) INTO total_price FROM cart WHERE user_id = 1;
    
    -- 5. 第二步：用 IF 语句做逻辑判断（如果满 100 就减 20）
    IF total_price >= 100 THEN
        SET total_price = total_price - 20;
    END IF;
    
    -- 6. 第三步：生成最终订单并扣款
    INSERT INTO orders (user_id, final_amount) VALUES (1, total_price);
    
    -- 7. 把结果展示出来
    SELECT total_price AS '最终要付的钱';
END //

-- 8. 恢复默认的结束符
DELIMITER ;

```

写完这段代码后，这套逻辑就永远保存在数据库里了。以后你想结算，只需要用 **`CALL`** 命令喊它的名字：

```sql
CALL `自动结算打折订单`();

```

只要短短一句，数据库就会自动帮你走完所有的运算、判断和写入流程！

## 第三阶段：深入本质（辩证地看待存储过程）

用马克思主义辩证法来看，存储过程虽然极其强大，但在现代互联网公司里，它的地位却经历了“从神坛跌落”的过程。我们来看看它的利与弊：

### 🌟 它的绝对优势（为什么传统金融、国企爱用？）

1. **极致的网络性能**：本来要发 10 条 SQL 语句（跑 10 趟网络），现在只要发一个 `CALL` 命令（跑 1 趟），网络延迟降到了最低。
2. **极高的安全性**：银行非常喜欢。前台柜员不需要有修改“账户余额表”的权限，他只需要有执行 `转账()` 存储过程的权限。这就杜绝了基层员工乱改底层核心表的风险。

### ⚠️ 它的致命缺陷（为什么现在的互联网大厂不爱用？）

1. **调试简直是噩梦**：在 Java 或 Python 里写错代码，工具会精准告诉你哪一行报错。而在存储过程里写了几百行 SQL，一旦出错，数据库给的报错信息极其模糊，排查起来让人抓狂。
2. **算力绑架（难以扩展）**：数据库的强项是“存取数据”，不是“做复杂数学运算”。如果把所有的 `IF...ELSE...` 和循环计算全塞进存储过程，数据库服务器的 CPU 会被瞬间榨干。
3. **极度缺乏可移植性**：MySQL 里的存储过程，你换到 Oracle 或 PostgreSQL 里，语法完全不一样，代码几乎要全部重写，导致公司被某个数据库厂商死死绑架。

**行业现状：** 现在的主流趋势是，把复杂的逻辑判断（IF/ELSE）放到外部的代码（如 Java/Python/Go）里去算，算出结果后，再把干净利落的指令发给数据库去执行。**让代码归代码，让存储归存储。**

这样一来，你就可以在长篇大论里尽情地按 `Enter` 来换行排版了。直到整段话全部写完，你最后按下 `Ctrl + Enter`，一整篇汇报才会作为一个整体发送出去。

## 第二阶段：理性认识（抽象为 SQL 的解析规则）

在数据库的世界里，那个默认的 `Enter` 发送键，就是 **分号（`;`）**。

* **普通 SQL 语句**：数据库解析器（那个负责读懂你代码的机器人）是一个极其机械的家伙。只要它眼角瞥见了一个分号 `;`，它就会立刻大喊：**“收到！这句话结束了，我马上执行！”**
* **存储过程的矛盾**：存储过程就像是那段“长篇大论”。它内部的 `BEGIN` 和 `END` 之间，包裹着好几句独立的 SQL 语句，而按照语法规定，**内部的每一句独立 SQL 都必须用 `;` 结尾**。

### 🚨 如果不改 DELIMITER，到底会发生什么灾难？

我们来看看如果不加 `DELIMITER //`，只用默认的 `;`，数据库会怎么误解你的代码：

```sql
CREATE PROCEDURE `自动结算`()
BEGIN
    DECLARE total DECIMAL;
    -- 🛑 数据库读到这里，看到了第一个分号！
    -- 它以为你写完了，立刻强行执行上面的半截代码！

```

**数据库的崩溃瞬间：**
数据库看到第一个 `;`，立刻截断代码跑去执行。结果它发现：

* “咦？你前面写了 `CREATE PROCEDURE` 和 `BEGIN`，怎么没有 `END` 就结束了？”
* “语法错误！残缺不全！”
然后它就会当场罢工，给你抛出一大串红色的 Syntax Error（语法错误）。

## 第三阶段：深入本质（偷天换日的 `DELIMITER`）

为了解决这个“发送键冲突”，数据库设计者给了你一个修改发送键的特权命令：**`DELIMITER`（定义结束符）**。

当你写下这套标准组合拳时，底层发生的事情如下：

```sql
-- 动作一：修改发送键
DELIMITER //  
-- 机器人的内心 OS：“好的，从现在开始，我只认 // 为执行命令。看到普通的分号 ; 我不管，那是单纯的标点符号。”

CREATE PROCEDURE `自动结算`()
BEGIN
    DECLARE total DECIMAL;       -- 遇到 ;，机器人不执行，继续往下读
    SELECT SUM(price)... ;       -- 遇到 ;，机器人不执行，继续往下读
    INSERT INTO orders... ;      -- 遇到 ;，机器人不执行，继续往下读
END // 
-- 🛑 动作二：完美发送
-- 机器人的内心 OS：“看到 // 了！这是一整块完整的代码，我把它整体打包编译，存进数据库！”

-- 动作三：恢复默认设置
DELIMITER ;
-- 机器人的内心 OS：“好的，改回默认设置，以后看到 ; 我就立刻执行。”

```

### 💡 核心总结

* **`DELIMITER //` 的本质，就是给数据库吃一颗“定心丸”**。告诉它：“待会儿无论在代码里看到多少个分号，都给我憋住别执行，直到看见 `//`，你再把它当成一个完整的整体一口气吞下去。”
* 你不仅可以用 `//`，很多老程序员也喜欢用 **`$$`**，效果是完全一样的（`DELIMITER $$`）。只要这个符号不会在你内部的 SQL 语句中出现，用什么当临时发送键都可以。

## 第一阶段：感性认识（为什么 `END` 靠不住？）

想象你在写一部长篇小说。

如果你跟出版社约定：“只要看到原稿里出现‘结束’这两个字，就代表全书写完了，可以直接拿去印刷。”
这听起来没问题，但如果你在小说的第三章写了一句台词：

> *男主角冷冷地说：“你们的阴谋到此**结束**了！”*

完了！出版社的机器看到“结束”两个字，立刻强行截断，直接把前三章拿去排版印刷，后面的大结局全扔了。

在数据库里，**`END` 就是极其容易引发这种误会的词！**
因为在复杂的存储过程里，`END` 实在是太常见了。你看下面这段代码：

```sql
CREATE PROCEDURE `复杂结账`()
BEGIN
    IF VIP_level = 1 THEN
        SET price = price * 0.8;
    END IF;  -- 🚨 这里有一个 END！

    WHILE count < 10 DO
        SET count = count + 1;
    END WHILE; -- 🚨 这里又有一个 END！
END //       -- 真正的结尾

```

如果系统只看 `END` 来决定是否结束，那么在读到 `END IF;` 的时候，它就以为整个存储过程大结局了，直接截断报错。这就是为什么 `END` 根本承担不起“定界符”的重任。

## 第二阶段：理性认识（揭开底层真相：DELIMITER 到底是在给谁下命令？）

这里有一个极其硬核、甚至很多工作了几年的程序员都不知道的底层真相：

> **`DELIMITER` 这个指令，根本就不是发给“数据库服务器（MySQL Server）”的，而是发给“数据库客户端（比如你用的 Navicat、DataGrip 或者黑乎乎的命令行窗口）”的！**

用唯物主义的架构观来看：

1. **客户端（前端收发发员）**：它的智商很低，它根本不懂什么是 `BEGIN` 什么是 `END`。它的唯一任务，就是**无脑收集你敲击的字符**。收集到什么时候为止？收集到看见“发送键（Delimiter）”为止。然后把收集到的一大坨文本，打包通过网线扔给远端的服务器。
2. **服务器（后台大厨）**：它才是真正懂 SQL 语法的聪明人。它收到包裹拆开后，才会去严谨地核对里面的 `BEGIN` 和 `END` 有没有成双成对。

**因果律推演：**
如果你不改 `DELIMITER //`，用的还是默认的分号 `;`。
你的**客户端（前端收发员）**在读到 `DECLARE total DECIMAL;` 时，看到了分号，它以为你写完了，立刻把这半截残缺的代码打包发给了**服务器（后台大厨）**。
大厨拆开一看：“这写的什么破烂？只有开头没有 `END`？”然后给你抛出一个无情的语法错误。

## 💡 终极总结

所以，你的直觉极其精准：

* **`DELIMITER //`** 是物理层面的“打包封箱胶带”，它告诉客户端：“把我用胶带缠起来的这整坨东西，原封不动地发走！”
* **`BEGIN ... END`** 才是逻辑层面的“起承转合”，它告诉服务器：“这里面是一个完整的业务逻辑块，请按顺序执行。”

## 第一阶段：感性认识（后厨的“传菜窗口”）

想象一下，存储过程就是后厨墙上的那张“标准操作指导书（SOP）”。
而紧跟在它名字后面的那个**括号 `()**`，就是连接前厅（你）和后厨（数据库）的“传菜窗口”。

如果你想让后厨干活，你不能光喊一句“做奶茶”，你得通过这个窗口，把具体的要求递进去，后厨做完后，再把成品从窗口递出来。

在这个窗口上，有三种不同的**物流方向**，分别对应着 `IN`、`OUT` 和 `INOUT`：

### 1. `IN`（送进去的原材料）

* **现实场景**：你把一张点餐单递进窗口：“**2 号桌，要 1 杯珍珠奶茶，少糖**。”
* **物理特征**：这个信息是你（外部）提供给厨师（内部）的。厨师照着做就行了，他绝对不会拿笔去涂改你这张点餐单。
* **本质**：**单向输入**。你把数据送进去，供里面使用。

### 2. `OUT`（端出来的空盘子）

* **现实场景**：你发现收银台缺零钱了，于是你往窗口里递了一个**空盒子**，对店长喊：“**帮我算一下今天的总营业额，然后把钱放进这个盒子里递给我！**”
* **物理特征**：你递进去的东西是没有初始内容的（或者里面有东西也会被倒掉）。厨师在里面噼里啪啦算完账，把最终结果装进盒子里，递还给你。
* **本质**：**单向输出**。你送进去一个“空容器”，指望它装满结果出来。

### 3. `INOUT`（进去加工一圈再出来）

* **现实场景**：你接到一个客人的退单，你端着一杯**做了一半的奶茶**递进窗口说：“**这杯奶茶客人嫌不够甜，你再往这杯子里加两勺糖，然后把这杯原物递还给我。**”
* **物理特征**：容器进去的时候**自带初始状态**，厨师在里面的操作是基于这个初始状态进行修改，最后把**修改后的成品**送出来。
* **本质**：**双向流通**。既是原料，又是装成品的容器。

---

## 第二阶段：理性认识（抽象为 SQL 的课本语法）

现在我们将传菜窗口的物流方向，严格映射到数据库的语法中：

| 参数方向 | 英文全拼 | 数据的流向 | 数据库的底层态度 | 日常使用频率 |
| --- | --- | --- | --- | --- |
| **`IN`** | Input | **外 $\rightarrow$ 内** | 默认模式（如果不写，默认就是 IN）。传入的值在存储过程内部可以被读取，但如果内部修改了它，**外部的原始数据不会跟着变**。 | ⭐⭐⭐⭐⭐ (90% 的场景全用它) |
| **`OUT`** | Output | **内 $\rightarrow$ 外** | 传入时，不管它原来有什么值，都会被清空为 `NULL`。它的唯一使命就是**把存储过程内部计算好的结果，带出到外部**。 | ⭐⭐⭐ (用来返回计算结果) |
| **`INOUT`** | Input/Output | **外 $\leftrightarrow$ 内** | 传入时带着初始值，内部基于初始值进行修改，执行完毕后，**修改后的新值会同步给外部**。 | ⭐ (极少使用，容易造成逻辑混乱) |

## 第三阶段：工业级代码实战（看看它们到底怎么配合）

为了让你彻底看清它们是怎么运作的，我们写一个同时包含了 `IN` 和 `OUT` 的完美存储过程：

**业务需求**：“给我算一下**某个特定员工（IN）**，在**某个特定月份（IN）**的总销售额，然后把算出来的钱**交给我（OUT）**。”

### 1. 编写存储过程（后厨定规矩）

```sql
DELIMITER //

CREATE PROCEDURE `查询员工月度业绩` (
    IN  emp_id INT,        -- 【送进去的原料】：要查哪个员工？
    IN  target_month INT,  -- 【送进去的原料】：要查哪个月份？
    OUT total_money DECIMAL(10,2) -- 【端出来的空盒子】：用来装算好的总钱数
)
BEGIN
    -- 厨师开始干活：按条件查询，并把查出来的总和（SUM），塞进（INTO）空盒子里
    SELECT SUM(price) INTO total_money 
    FROM orders 
    WHERE employee_id = emp_id AND MONTH(order_date) = target_month;
END //

DELIMITER ;

```

### 2. 调用存储过程（前厅下达指令）

这个时候，我们上一节学的用户变量（带有 `@` 的便利贴）就派上大用场了！因为你需要用一个变量来充当那个“空盒子”，接住后厨递出来的钱。

```sql
-- 动作 1：你撕下一张便利贴当空盒子，名字叫 @money_box
-- 动作 2：呼叫后厨！传入原料（3号员工，5月份），递进空盒子（@money_box）
CALL `查询员工月度业绩`(3, 5, @money_box);

-- 动作 3：执行完毕后，后厨已经把钱写在便利贴上了。你只需要查看便利贴即可！
SELECT @money_box AS '3号员工5月份的业绩';

```

---

### 💡 核心总结

这就是 `()` 里面那串复杂语法的全部真相：

* **数据类型（如 INT, VARCHAR）**：规定了这个传菜窗口只能递什么形状的东西。
* **`IN`**：你向数据库下达的具体“参数条件”。
* **`OUT`**：你向数据库索要的“计算结果”，必须用 `@变量` 去接住它。

    A:  哈哈，这次你可错怪工具啦！VSCode 委屈地表示：“这个锅我绝对不背！”

这一次，是彻彻底底的 **MySQL 官方原生语法错误**。问题出在你给存储过程名字加的那个标点符号上：**单引号（`'`）**。

我们继续用“透过现象看本质”的方法，来认清数据库世界里最容易混淆的两个标点符号：**单引号** vs **反引号**。

---

## 第一阶段：感性认识（“杯子里的奶茶”与“杯子上的标签”）

在现实生活中，我们要区分两样东西：

1. **内容物（数据）**：杯子里面装的“珍珠奶茶”。
2. **名字/标签（标识符）**：杯子外面贴的标签纸，上面写着“3号杯”。

如果你对服务员说：“给我扔掉‘珍珠奶茶’。”服务员会懵逼，因为珍珠奶茶是液体（数据内容），你没法直接扔液体，你只能扔那个叫“3号杯”的杯子（物理对象）。

---

## 第二阶段：理性认识（抽象为 SQL 的符号铁律）

在 MySQL 的语法解析器中，对这两样东西有极其严格的符号隔离：

### 1. 单引号 `' '`（代表：内容物/数据值）

* **作用**：专门用来包裹**普通的字符串数据**。
* **场景**：常用于 `WHERE` 条件、`INSERT` 插入的具体数值中。
* **例子**：`WHERE name = '张伟'`。数据库认为“张伟”是存在硬盘里的一段数据。

### 2. 反引号 `` ``（代表：对象的名字/标签）

* **按键位置**：在键盘左上角，`Esc` 键的下面，数字 `1` 的左边（要在英文输入法下敲击）。
* **作用**：专门用来包裹**数据库里的各种“实体对象的名字”（标识符）**，比如表名、列名、数据库名、存储过程名。
* **场景**：用于 `CREATE`、`DROP`、`SELECT` 后面的字段名。
* **例子**：`DROP PROCEDURE \`查询员工月度业绩`;`。数据库认为这是一个客观存在的程序名字。

---

## 🚨 破案时刻：你的代码为什么报错？

当你写下：

```sql
DROP PROCEDURE IF EXISTS '查询员工月度业绩';

```

数据库解析器看到**单引号**，它的内心 OS 是：

> *“主人让我删掉一个存储过程，但我往后一看，发现了一个单引号包裹的字符串数据（就像一杯液体的珍珠奶茶）？名字呢？语法不通啊！”*

### ✅ 正确的写法（两种都可以）

**方法一：使用反引号（最标准、最安全，特别是名字里有中文或空格时）**

```sql
DROP PROCEDURE IF EXISTS `查询员工月度业绩`;

```

**方法二：什么符号都不加（如果名字是纯英文且没有空格，通常可以直接裸奔，中文在大部分现代数据库里裸奔也行）**

```sql
DROP PROCEDURE IF EXISTS 查询员工月度业绩;

```

把单引号改成反引号（或者直接删掉单引号），再去执行一下，这个存储过程就会被干净利落地抹除了！记住这个铁律：**数据用单引，名字用反引（或不加）。**




9.  **事务：**
在真实的商业世界里，代码写得漂不漂亮是次要的，**数据绝不能算错账**才是唯一的底线。为了守住这条底线，数据库发明了“事务”。我们继续用“从具体到抽象”的认识论方法，回到咱们的奶茶店，来看看这个终极保镖是怎么工作的。

---

## 第一阶段：感性认识（奶茶店的“断电惊魂”）

想象一下，你的奶茶店推出了“VIP 储值卡”功能。今天，顾客张伟卡里有 100 元，他来买了一杯 20 元的奶茶。

作为收银系统，你（数据库）需要在后台执行两个极其关键的动作：

* **动作一**：从张伟的 VIP 卡余额里，扣除 20 元。（余额变成 80 元）
* **动作二**：在店里的“今日收入账本”上，增加 20 元。

**可怕的物理意外发生了：**
当机器刚刚飞速执行完“动作一”（张伟的钱已经被扣了），突然**停电了**！服务器瞬间宕机，“动作二”根本没来得及执行。

等来电重启后，你绝望地发现：张伟卡里莫名其妙少了 20 块钱，但你店里的账本上根本没有多出这 20 块钱。这笔钱在数字世界里**凭空蒸发**了！如果这是在银行，这就是极其严重的金融事故。

**现实世界的解决方案：**
你需要一种“时光倒流”的魔法。你希望对系统定下一个铁律：“**这两个动作，要么全部成功；只要中间有任何一步失败了，就立刻把时间倒流回第一个动作发生之前的状态，当做无事发生！**”

---

## 第二阶段：理性认识（抽象为“事务”与三大指令）

在数据库中，这种把多个动作“捆绑成一个生死与共的整体”的机制，就叫做**事务（Transaction）**。

你可以把它理解为一个“暂存的沙盘”。当你开启事务后，你所有的 SQL 动作都是在沙盘里演练，只有当你大喊一声“敲定！”，沙盘里的结果才会真正刻进硬盘里；如果中间搞砸了，你大喊一声“掀桌子！”，沙盘就会瞬间复原。

对应到 SQL 语法中，就是三个极其霸道的指令：

1. **`START TRANSACTION;` （开启事务）**
* 机器人的内心 OS：“好的，从现在开始，后面发生的所有修改操作，我都先放在沙盘里，绝对不马上写进物理硬盘！”


2. **`COMMIT;` （提交 / 敲定）**
* 机器人的内心 OS：“所有动作顺利完成，确认无误！现在，把沙盘里的结果一次性、永久地刻进物理硬盘里！”


3. **`ROLLBACK;` （回滚 / 时光倒流）**
* 机器人的内心 OS：“不好，中间报错了！立刻把沙盘清空，把数据恢复到执行 `START TRANSACTION` 之前的最初模样！”



**完美避开断电危机的代码结构：**

```sql
START TRANSACTION; -- 【开启沙盘演练】

-- 动作一：张伟扣钱
UPDATE vip_cards SET balance = balance - 20 WHERE user = '张伟';

-- 动作二：账本加钱
UPDATE shop_accounts SET total = total + 20 WHERE account = '本店';

-- 如果上面两步都顺顺当当没报错，程序就会执行下面这句：
COMMIT;  -- 【一锤定音，永久保存】

-- 如果中间突然断电或者报错，聪明的外部程序就会捕捉到异常，向数据库发送：
-- ROLLBACK; 【时光倒流，张伟的钱瞬间恢复成 100】

```

## 第三阶段：深入本质（事务的 ACID 四大物理定律）

用马克思主义的物质观来看，事务的出现，是为了在极度不稳定的计算机环境（随时可能断电、断网、死机）中，**捍卫现实客观世界的物质守恒定律**。

为了达到这个目的，数据库系统在底层给事务赋予了四种极其强大的物理特性，这就是面试中必考的 **ACID 原则**：

| 字母 | 核心特性 | 英文全称 | 哲学本质与现实意义 |
| --- | --- | --- | --- |
| **A** | **原子性** | **A**tomicity | **“生死与共，不可分割”**。原子在早期物理学中被认为是最小单位。事务里的 10 条语句就像一个原子，要么一起成功，要么一起失败，绝对没有“成功一半”的状态。 |
| **C** | **一致性** | **C**onsistency | **“物质守恒，规则不破”**。事务执行前后，绝对不能破坏我们在上一课讲的“数据库约束（如非空、唯一、余额不能为负数）”。现实世界的业务总账必须是对得上的。 |
| **I** | **隔离性** | **I**solation | **“平行宇宙，互不干扰”**。假设同一秒钟，张伟用手机买奶茶，他老婆也拿着同一张卡的副卡在买蛋糕。数据库必须像“排队过安检”一样，把这两个同时发生的事务隔离开，不能让他们互相看到对方算了一半的糊涂账。 |
| **D** | **持久性** | **D**urability | **“刻碑立传，不可磨灭”**。只要事务执行了 `COMMIT`，那么哪怕下一毫秒整个机房的电缆被挖断了，当服务器再次重启时，这笔改动也绝不会丢失。 |

可以说，整个现代金融体系的基石，就建立在关系型数据库的 ACID 物理定律之上。没有它们，你在淘宝、微信上的每一笔付款都是在“赌运气”。

## 第一阶段：感性认识（张伟夫妇的“双十一抢单大作战”）

到了“双十一”零点，奶茶店推出了限量秒杀的 80 元情侣套餐。
张伟和老婆在外地出差，但他们共享同一张 VIP 卡，卡里刚好只有 **100 元**。两人都在零点零分零秒，同时按下了手机上的“立即付款”按钮。

### 🚨 灾难重演：如果没有隔离保护会怎样？

两部手机（两个并发事务）几乎在同一纳秒连接到了数据库：

1. **张伟的事务**探头看了一眼余额：“有 100 块，大于 80，可以扣款！”
2. 就在张伟的事务还没来得及扣钱的瞬间，**老婆的事务**也探头看了一眼：“有 100 块，大于 80，可以扣款！”
3. 张伟的事务执行扣款：`100 - 80 = 20`，把 20 写入系统。
4. 老婆的事务执行扣款：它以为余额还是 100，也执行 `100 - 80 = 20`，把 20 写入系统。

**结局：** 奶茶店发了两份 80 元的套餐，但 VIP 卡里居然还剩 20 元！老板亏得底裤都没了。这在数据库里被称为“丢失更新（Lost Update）”。

## 第二阶段：理性认识（抽象为底层的“锁机制”）

现实世界中，为了防止两个人同时抢一个厕所隔间，我们会怎么做？**加锁！**
数据库也是一样，工程师们发明了两种截然不同的锁哲学：

### 1. 悲观锁（Pessimistic Lock）—— “总有刁民想害朕”

* **现实操作**：张伟的事务一查余额，立刻**把这张 VIP 卡用一把大铁锁锁死**！在这期间，老婆的手机会一直显示“加载中（转圈圈）”。直到张伟扣完钱，解开大铁锁，老婆的事务才能进去查余额，此时她会发现余额变成 20 了，系统提示“余额不足”。
* **底层语法**：在 SQL 里加上 `FOR UPDATE`。
`SELECT balance FROM vip_cards WHERE user = '张伟' FOR UPDATE;`
* **利弊**：绝对安全，但非常影响效率（后面的人全得排队傻等）。

### 2. 乐观锁（Optimistic Lock）—— “世界充满爱”

* **现实操作**：不加物理锁，而是给 VIP 卡加上一个“版本号”**。
初始状态：余额 100，**版本号 1**。
张伟和老婆同时看到了“版本号 1”。张伟手速快了 1 毫秒，先扣完钱，把余额改成了 20，并把**版本号升级为 2。
紧接着老婆的系统发来指令：“请把余额改成 20，**前提是当前版本号必须是 1**”。数据库一看，现在版本号已经是 2 了，当场拒绝老婆的请求，提示“网络繁忙，请重试”。
* **利弊**：极大地提升了系统的并发吞吐量，是现在高并发互联网大厂最爱用的招数！

## 第三阶段：深入本质（四大隔离级别 Isolation Levels）

每次写代码都要手动加锁太麻烦了，而且容易写出死锁（互相锁死）。于是，数据库系统在宏观层面上，直接给你提供了四档预设好的“防御护盾”，这就是面试中必问的“事务隔离级别”。

这四个级别就像打怪升级，越往后越安全，但系统运行越慢。

| 隔离级别 | 护盾厚度 | 现实中的糟糕现象 | 它的核心表现 |
| --- | --- | --- | --- |
| **1. 读未提交**<br>

<br>(Read Uncommitted) | **无护盾**（相当于裸奔） | 🚨 **脏读（Dirty Read）** | 张伟在沙盘里刚把钱改成 20（还没点 COMMIT 敲定），老婆就能看到 20。如果张伟后来按了 `ROLLBACK` 退款了，老婆看到的 20 就是不存在的假数据（脏数据）。 |
| **2. 读已提交**<br>

<br>(Read Committed) | **薄护盾**（防脏读） | 🚨 **不可重复读** | 老婆只能看到张伟 `COMMIT` 之后的钱。但老婆在这个月内查了两次账：月初查是 100，月末查变成了 20。在一个事务内，两次看到的数据不一样。 |
| **3. 可重复读**<br>

<br>(Repeatable Read) | **中等护盾**（MySQL 默认等级） | 🚨 **幻读（Phantom Read）** | **这是 MySQL 最牛的地方！** 当老婆开启事务时，数据库会给世界拍个“快照”。不管外面张伟怎么折腾，老婆只要不退出这个事务，她无论查多少次，看到的余额永远是 100。仿佛在一个被隔离的平行宇宙里。 |
| **4. 串行化**<br>

<br>(Serializable) | **绝对无敌防御** | **无**（极其安全但也极其慢） | 数据库彻底变成单行道。所有涉及同一种数据的事务，哪怕只是读取，也必须乖乖排成一条直线，一个执行完才能执行下一个。 |

---

### 💡 哲学的总结

回顾一下，其实数据库的“并发控制”就是在做一道极其艰难的**天平权衡题**：

* 天平的左边是 **安全性（隔离级别越高越好，锁越紧越好）**。
* 天平的右边是 **性能吞吐量（不能让顾客看着手机一直转圈圈等排队）**。

MySQL 为什么默认选择“可重复读（Repeatable Read）”？因为它找到了性能和安全之间最完美的中庸之道。

想象一下，你写了一个名叫 `做一杯珍珠奶茶()` 的存储过程（后厨的自动化操作手册）。

**1. 没有处理器的时代（直接原地爆炸）**

**2. 有了异常处理器的时代（从容不迫的“急救预案”）**
聪明的店长会在操作手册的最前面，加一段红字标明的“应急预案”：

> **“如果在做奶茶的任何环节发生了任何意外报错，不要慌，立刻停止手头的活，去执行以下操作：把做了一半的废料倒进垃圾桶，给顾客退钱，并微笑着对顾客说‘对不起，系统开了个小差’。”**

这就是异常处理器！就算厨房真的着火了，厨师也会有条不紊地完成退款、安抚顾客，然后优雅地退出。

## 第二阶段：理性认识（抽象为 SQL 语法与定义）

在数据库（MySQL）中，这个应急预案的专业术语叫做 **异常处理程序（Condition Handler）**。

`SQLEXCEPTION` 是其中最广谱、最强大的一种，它代表：**“任何导致程序无法正常运行的 SQL 报错”**。

### 💡 核心语法公式

你必须把这个急救包，放在存储过程 `BEGIN` 之后的**变量声明的紧后面**，**具体干活的代码的前面**。

```sql
DECLARE 动作规则 HANDLER FOR SQLEXCEPTION
BEGIN
    -- 这里写：一旦发生了报错，系统要立刻跳过来执行的“擦屁股代码”
END;

```

这里的“动作规则”有两种最常见的选择：

1. **`EXIT`（退出）**：一旦发生异常，执行完擦屁股代码后，**直接结束并退出**整个存储过程。（最常用，相当于“锅砸了，退钱，下班！”）
2. **`CONTINUE`（继续）**：一旦发生异常，执行完擦屁股代码后，**当做无事发生，继续去执行下一句 SQL**。（极少用，除非你对错误完全不在乎）。

## 第三阶段：深入本质（完美的实战形态：事务 + 异常处理器）

你上一节刚刚学过了事务（Transaction）的 `START TRANSACTION`、`COMMIT` 和 `ROLLBACK`。

但在现实中，如果你写了 `START TRANSACTION`，当中间的代码报错崩溃时，程序根本走不到最后一步的 `ROLLBACK` 去，怎么办？

**答案是：把它们缝合在一起！这也是千万级互联网大厂写存储过程的“终极标准工业模板”！**

我们来看一段完美的、绝对不会让钱凭空消失的“安全扣款”代码：

```sql
DELIMITER //

CREATE PROCEDURE `绝对安全的VIP扣款`(IN user_name VARCHAR(20), IN deduct_money DECIMAL(10,2))
BEGIN
    -- 1. 声明急救包（EXIT HANDLER）
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        -- 【应急动作 1】：发生任何报错，立刻进行“时光倒流”，把钱退回去！
        ROLLBACK;
        -- 【应急动作 2】：给前端返回一句人话，而不是抛出乱码报错
        SELECT '交易失败：系统发生异常，已自动为您退款。' AS Result;
    END;

    -- 2. 正常流程开始：开启沙盘演练
    START TRANSACTION;
    
        -- 步骤 A：扣除余额
        UPDATE vip_cards SET balance = balance - deduct_money WHERE user = user_name;
        
        -- 步骤 B：记录流水账 (假设这里我们故意把表名 shop_logs 写错了，写成了 shop_logssss)
        -- 🚨 数据库执行到这句时会突然报错！
        INSERT INTO shop_logssss (user, amount) VALUES (user_name, deduct_money);
        
    -- 3. 如果上面一切顺利（没有触发报错），就会顺利执行敲定
    COMMIT;
    SELECT '交易成功！' AS Result;

END //

DELIMITER ;

```

### 🧠 底层时空运转逻辑分析：

1. 程序开启了事务。
2. 顺利执行了“步骤 A”，张伟的钱在沙盘里被扣了。
3. 执行到“步骤 B”时，突然发现表名不存在，**系统抛出底层异常**。
4. 就在系统准备崩溃报警的瞬间，隐藏在暗处的 **`SQLEXCEPTION EXIT HANDLER`（急救包）** 突然被激活！
5. 系统瞬间跳过后面的 `COMMIT`，直接飞进急救包里，执行了 **`ROLLBACK;`**！
6. 张伟被扣的钱瞬间恢复，程序优雅地吐出一句“交易失败：系统发生异常”，然后和平退出。

你看，**这就是技术世界里的“兜底思维”**。优秀的工程师从不相信代码会永远顺利运行，他们永远会为最坏的情况准备好 `SQLEXCEPTION` 急救包。

## 第一阶段：感性认识（“拔腿就跑” vs “紧急操作手册”）

想象一下，你们办公室墙上贴着“火灾应急预案”。

* **情况一：极简预案（只有一个动作）**
预案上只写了四个大字：**“赶紧跑路！”**
因为只有一个动作，不需要分步骤，所以完全不需要拿个夹子把它装订成一本手册，直接贴墙上就行了。
* **情况二：复杂预案（有多个动作）**
预案上写着：
“1. 切断电源；
2. 拨打 119；
3. 拿起灭火器；
4. 赶紧跑路。”
因为动作太多了，你必须用一个“文件夹（手册）”把这四句话装订在一起，告诉大家：“这四步是一个完整的应急整体流程。”

---

## 第二阶段：理性认识（抽象为 SQL 语法规则）

在 SQL 里，**`BEGIN ... END` 就是那个“文件夹”**。它的唯一作用，就是把多条 SQL 语句打包成一个复合语句块（Compound Statement）。

根据这个规律，`SQLEXCEPTION` 处理器就衍生出了两种合法的写法：

### 1. “拔腿就跑”写法（极简版，不用 BEGIN/END）

当你遇到异常时，如果**只需要执行 1 个动作**（比如只要回滚，别的啥也不干），你完全可以省掉文件夹，直接把动作跟在后面。

* **工业极简代码：**
```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION ROLLBACK;

```


*(翻译：只要报错，立刻回滚，结束！)*
你看到的别人的代码，大概率就是这种极其干净利落的单行写法。

### 2. “紧急操作手册”写法（豪华版，必须用 BEGIN/END）

如果你遇到异常时，**需要执行 2 个或 2 个以上的动作**（比如既要回滚，又要向日志表里插一条报错记录，还要给前端返回一段话），那你就**必须**用 `BEGIN ... END` 把它们包起来。如果你不包，系统就不知道到底哪几句属于急救包。

* **工业标准复合代码：**
```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION 
BEGIN  -- 文件夹开启
    ROLLBACK;                                  -- 动作 1：回滚
    INSERT INTO error_logs VALUES ('发生报错'); -- 动作 2：记日记
    SELECT '系统崩溃啦！' AS msg;                -- 动作 3：通知前端
END;   -- 文件夹关闭

```



---

## 💡 终极扩展：这个规则不仅适用于处理器！

掌握了这个“单行 vs 多行”的规律，你会发现整个 SQL 编程（包括触发器、循环、条件判断）瞬间变得极其通透。

比如你在写 `IF` 判断时，如果有多个动作，你要写 `BEGIN...END`；但在写 `WHILE` 循环或者其他的结构时，只要核心动作只有一条，很多时候数据库底层也允许你省略块结构（具体取决于不同的数据库方言）。

所以，代码里带不带 `BEGIN...END`，完全取决于你手里捏着的是“一个指令”，还是“一堆指令的集合”！
