**第一节变量**

在实际的数据库运维和开发中，因为“系统变量”的作用范围差异巨大，所以大家通常会把系统变量一分为二：**全局变量** 和 **会话变量**。

这样一来，就凑齐了你看到的“四大变量家族”：

1. **全局变量（Global Variables）** ── 属于系统变量
2. **会话变量（Session Variables）** ── 属于系统变量
3. **用户变量（User Variables）** ── 开发者自定义（带 `@`）
4. **局部变量（Local Variables）** ── 代码块内部专属（`DECLARE`）

我们继续运用“从具体到抽象”**的方法，把这四种变量放在**“连锁奶茶店”的场景里，你就能秒懂它们各自的地位和脾气。

## 第一阶段：感性认识（连锁奶茶店的四个“记事本”）

假设你现在是“连锁奶茶店”的总工程师，负责给所有门店的收银机电脑设计系统。

### 1. 全局变量（Global）：【总公司的全国统一规章】

* **现实场景**：总公司规定，全中国所有的分店、所有的收银机，默认的“自动退单超时时间”统一为 **30 分钟**。
* **特点**：只要你在总公司后台改了这个数字，全全国所有正在开机的、未来要开机的电脑，**全部生效**。它影响的是“整个数据库服务器”。

### 2. 会话变量（Session）：【某个分店收银机的当班设置】

* **现实场景**：今天北京分店的网速极慢，店长觉得 30 秒超时太短了，于是他在**自己这台收银机**上临时修改：“我这台电脑的超时时间改为 **60 秒**”。
* **特点**：这只影响他**眼前这台电脑**（当前的连接/会话）。别的分店电脑依然是 30 秒；而且等他晚上关机重启，这台电脑又会恢复成总公司的默认值。

### 3. 用户变量（User）：【收银员自己贴的“便利贴”】

* **现实场景**：收银员小明在算账，随手在屏幕旁贴了张便利贴 `@temp_price = 100`。
* **特点**：带有 **`@`** 符号。这个便利贴是小明私人建立的，只在小明登录的这几个小时里有用。小明下班注销账号，便利贴就被保洁阿姨撕掉扔了。

### 4. 局部变量（Local）：【打印小票程序里的“临时计算草稿纸”】

* **现实场景**：收银机内部有一段自动打折的代码，在计算“满100减20”的瞬间，代码内部产生了一个临时的草稿纸 `discount = 20`。
* **特点**：用 **`DECLARE`** 声明。只在这一段特定的计算代码（存储过程/函数）运行的那几毫秒里存在，小票打印完的瞬间，草稿纸就灰飞烟灭了。

## 第三阶段：深入语法与实战细节

为了让你在看别人写的复杂 SQL 时不再迷路，我们把这四种变量的代码形态一一拆解：

### 1. 全局变量 (Global System Variables)

这是数据库管理员（DBA）最常调整的东西，比如修改数据库的最大连接数、时区、缓存大小。

```sql
-- 查看数据库当前的全局时区设置
SELECT @@global.time_zone;

-- 修改全局最大连接数为 1000（影响后续所有连接）
SET GLOBAL max_connections = 1000;

```

### 2. 会话变量 (Session System Variables)

当你连接上数据库时，数据库会把全局变量**复制一份**给你作为你的“会话变量”。你在自己窗口里改会话变量，不会影响别人。

```sql
-- 查看我当前这个窗口的自动提交设置
SELECT @@session.autocommit;

-- 临时关闭我这个窗口的自动提交（不影响其他正在工作的同事）
SET SESSION autocommit = 0;
-- 简写（省略 SESSION，默认就是改会话）：
SET @@autocommit = 0;

```

### 3. 用户变量 (User-defined Variables)

这是你在写日常 SQL 查询脚本时**最常用**的临时存储工具。不需要提前指定数据类型，直接带 `@` 就能用。

```sql
-- 定义一个用户变量，把全校最高分存进去
SET @top_score = (SELECT MAX(score) FROM students);

-- 随时调用这个便利贴
SELECT * FROM students WHERE score = @top_score;

```

### 4. 局部变量 (Local Variables)

它只能写在数据库的存储过程（Stored Procedure）**或者**函数（Function）的内部，用来做复杂的自动化逻辑计算。必须先定义数据类型，才能使用。

```sql
DELIMITER //
CREATE PROCEDURE calculate_tax()
BEGIN
    -- 1. 必须在开头用 DECLARE 声明局部变量（无前缀，必须指定类型）
    DECLARE total_sales DECIMAL(10,2);
    DECLARE tax_rate DECIMAL(4,2) DEFAULT 0.05;
    
    -- 2. 给局部变量赋值
    SELECT SUM(price) INTO total_sales FROM orders;
    
    -- 3. 使用局部变量计算
    SELECT total_sales * tax_rate AS final_tax;
END //
DELIMITER ;

```

## 💡 快速记忆符号秘籍

以后你在代码里看到变量，只需要**看它的“前缀”**，就能瞬间判断它的身份：

1. **没有 `@` 符号，且开头写着 `DECLARE**` $\rightarrow$ **局部变量**（草稿纸，只活在代码块里）。
2. **只有一个 `@` 符号（如 `@my_var`）** $\rightarrow$ **用户变量**（便利贴，跟你这个连接同寿命）。
3. **有两个 `@@` 符号（如 `@@global.xxx` 或 `@@session.xxx`）** $\rightarrow$ **系统变量**（数据库的控制开关）。
* 带 `global` 是影响大家的**全局变量**。
* 带 `session`（或什么都不带）是只影响你自己的**会话变量**。



2.  变量小细节：
     SELECT @@GLOBAL.xxx 是去数据库“金库”里直接拿原始数据，拿出来的是底层存储的真实值（0 和 1）；
     SHOW GLOBAL VARIABLES 是经过 MySQL“前台接待”包装过的展示界面，把 0/1 翻译成了人类爱看的 ON/OFF。




3.  Q：为啥用SELECT赋值时只能用“：=”来赋值？
    A：这个问题问得极具穿透力！你敏锐地察觉到了 SQL 语法设计中一个非常经典、但也最容易让初学者抓狂的“双标”现象。

为什么 `SET @a = 1` 可以，而 `SELECT @a = 1` 就不行，非得写成 `SELECT @a := 1` 呢？

我们继续用“透过现象看本质”的方法，深入到**数据库解析器（SQL Parser）的大脑**里，看看它为什么会在这里产生“逻辑精神分裂”。

## 第一阶段：感性认识（现实生活中的“一词多义”歧义）

想象一下，你用中文对一个并不聪明的机器人助理说了一句话：

> **“小明是 18 岁。”**

这句话在人类语言里，其实潜藏着**两种完全不同的物理动作**：

1. **赋值（命令）**：“去，把小明的档案拿出来，把他的年龄**修改/设置**为 18 岁。”
2. **比较（提问）**：“你去查一下，小明现在的年龄**等于** 18 岁吗？”（机器人的回答应该是“是”或“不是”）。

你看，同一个“是”（对应数学符号 `=`），因为语境的不同，产生了歧义。为了不让机器人发疯，你必须用更精准的词汇来限定你的意图。

---

## 第二阶段：理性认识（抽象为数据库的“符号歧义”）

在 SQL 语言的底层设计中，等号 **`=`** 天生就是一个“比较运算符”（相当于 Python 或 Java 里的 `==`）。它的第一天职，是用来判断左右两边相不相等。

我们来看看数据库解析器在不同语境下，是如何理解 `=` 的：

### 1. 为什么在 `SET` 后面可以用 `=`？（有明确语境）

当你写下：

```sql
SET @age = 18;

```

数据库解析器读到第一个词 **`SET`（设置）** 的时候，它的大脑就进入了“赋值模式”。它知道你接下来要干嘛，所以当它看到后面的 `=` 时，它能百分之百确定：这里的 `=` 不是在提问，而是在下达**赋值**命令。所以它顺理成章地把 18 存进了 `@age`。

### 2. 为什么在 `SELECT` 后面用 `=` 会引发灾难？（语境错乱）

当你写下：

```sql
SELECT @age = 18;

```

解析器读到第一个词 **`SELECT`（查询/提取）** 时，它的大脑进入的是“提问模式”。
此时，它看到后面的 `@age = 18`，它会本能地把它当成一个**判断题**：

> *“主人是在问我，变量 `@age` 里面的值，是不是等于 18 呀？”*

于是，数据库会在底层做这样的运算：

* 如果 `@age` 之前刚好被存过 18，数据库会在屏幕上输出 **`1`（代表 True / 正确）**。
* 如果 `@age` 是空的或者存的是别的数字，数据库会在屏幕上输出 **`0`（代表 False / 错误）**。

**结论：在 `SELECT` 语句中，如果你写 `=`，数据库根本没有为你“赋值”，它只是在默默地做了一道“判断题”，然后把判断结果（0 或 1）告诉了你。**

## 第三阶段：深入本质（拯救歧义的专属符号 `:=`）

为了解决 `SELECT` 语句中这个极其致命的歧义，数据库的设计者们不得不引入一个新的符号来强行破局。

他们借鉴了早期编程语言（如 Pascal）中的语法，把冒号和等号拼在了一起：**`:=`**。

这个符号在数据库里拥有唯一的、绝对的物理含义：**纯粹的赋值运算**。
它身上没有任何“判断/比较”的基因。

当你写下：

```sql
SELECT @age := 18;

```

数据库解析器看到 `:=` 的瞬间，所有的歧义都烟消云散了。它立刻明白：

> *“不管我在什么模式下，只要看到 `:=`，主人的意思就是绝对的死命令——**把右边的 18 强行塞进左边的 `@age` 里，并且把这个 18 展示出来！***”

---

### 💡 终极防坑总结图

为了让你的肌肉产生永久记忆，请看这组核心对比：

| SQL 语句 | 数据库的内心 OS (如何理解？) | 实际发生的结果 | 屏幕展示的值 |
| --- | --- | --- | --- |
| `SET @a = 1;` | “有 SET 罩着，我知道这是让我把 1 存进 `@a`。” | **成功赋值** | (无展示，默默执行) |
| `SELECT @a = 1;` | “SELECT 模式下遇到 `=`，这是在问我 `@a` 等不等于 1。” | **根本没有赋值！只做了判断。** | `0` 或 `1` (True/False) |
| `SELECT @a := 1;` | “遇到 `:=` 死命令，立刻把 1 存进 `@a`，然后输出。” | **成功赋值** | `1` (你赋进去的值) |

这就是为什么在高级的 SQL 脚本里，只要你想在 `SELECT` 查询的过程中“顺手”抓取数据存入变量，就必须、也只能使用 `:=` 的根本原因。

假设你开了一家大型餐厅，你（前端程序员）在前面做服务员，数据库（MySQL）是后厨。

你发现问题了吗？为了做一道菜，你在前厅和后厨之间**来回跑了 4 趟（发生了 4 次网络通信）**。如果今天店里有 1000 个客人，你的腿（网络带宽）都要跑断了。

## 第二阶段：理性认识（抽象为课本定义与代码）

我们将生活场景翻译成数据库语言。

**课本定义：**

> **存储过程（Stored Procedure）**是一组为了完成特定功能的 SQL 语句集合。它经过编译后**直接存储在数据库服务器内部**。用户只需要通过指定存储过程的名字，就可以呼叫并自动执行这整套逻辑。

### 💡 工业级代码演示：如何写一份“后厨 SOP”

假设我们要写一个打折结算的存储过程。你会发现，上一节学的局部变量（DECLARE）在这里大显身手了：

```sql
-- 1. 告诉数据库：先把语句结束符由分号 ; 改为 //，防止写到一半数据库以为写完了
DELIMITER //

-- 2. 开始写 SOP（创建存储过程）
CREATE PROCEDURE `自动结算打折订单`()
BEGIN
    -- 3. 拿出局部变量（草稿纸）
    DECLARE total_price DECIMAL(10,2);
    
    -- 4. 第一步：算总价
    SELECT SUM(price) INTO total_price FROM cart WHERE user_id = 1;
    
    -- 5. 第二步：用 IF 语句做逻辑判断（如果满 100 就减 20）
    IF total_price >= 100 THEN
        SET total_price = total_price - 20;
    END IF;
    
    -- 6. 第三步：生成最终订单并扣款
    INSERT INTO orders (user_id, final_amount) VALUES (1, total_price);
    
    -- 7. 把结果展示出来
    SELECT total_price AS '最终要付的钱';
END //

-- 8. 恢复默认的结束符
DELIMITER ;

```

写完这段代码后，这套逻辑就永远保存在数据库里了。以后你想结算，只需要用 **`CALL`** 命令喊它的名字：

```sql
CALL `自动结算打折订单`();

```

只要短短一句，数据库就会自动帮你走完所有的运算、判断和写入流程！

## 第三阶段：深入本质（辩证地看待存储过程）

用马克思主义辩证法来看，存储过程虽然极其强大，但在现代互联网公司里，它的地位却经历了“从神坛跌落”的过程。我们来看看它的利与弊：

### 🌟 它的绝对优势（为什么传统金融、国企爱用？）

1. **极致的网络性能**：本来要发 10 条 SQL 语句（跑 10 趟网络），现在只要发一个 `CALL` 命令（跑 1 趟），网络延迟降到了最低。
2. **极高的安全性**：银行非常喜欢。前台柜员不需要有修改“账户余额表”的权限，他只需要有执行 `转账()` 存储过程的权限。这就杜绝了基层员工乱改底层核心表的风险。

### ⚠️ 它的致命缺陷（为什么现在的互联网大厂不爱用？）

1. **调试简直是噩梦**：在 Java 或 Python 里写错代码，工具会精准告诉你哪一行报错。而在存储过程里写了几百行 SQL，一旦出错，数据库给的报错信息极其模糊，排查起来让人抓狂。
2. **算力绑架（难以扩展）**：数据库的强项是“存取数据”，不是“做复杂数学运算”。如果把所有的 `IF...ELSE...` 和循环计算全塞进存储过程，数据库服务器的 CPU 会被瞬间榨干。
3. **极度缺乏可移植性**：MySQL 里的存储过程，你换到 Oracle 或 PostgreSQL 里，语法完全不一样，代码几乎要全部重写，导致公司被某个数据库厂商死死绑架。

**行业现状：** 现在的主流趋势是，把复杂的逻辑判断（IF/ELSE）放到外部的代码（如 Java/Python/Go）里去算，算出结果后，再把干净利落的指令发给数据库去执行。**让代码归代码，让存储归存储。**

**你怎么解决这个问题？**
你会去微信的设置里，把“发送快捷键”从默认的 **`Enter`**，临时修改为 **`Ctrl + Enter`**。
这样一来，你就可以在长篇大论里尽情地按 `Enter` 来换行排版了。直到整段话全部写完，你最后按下 `Ctrl + Enter`，一整篇汇报才会作为一个整体发送出去。

## 第二阶段：理性认识（抽象为 SQL 的解析规则）

在数据库的世界里，那个默认的 `Enter` 发送键，就是 **分号（`;`）**。

* **普通 SQL 语句**：数据库解析器（那个负责读懂你代码的机器人）是一个极其机械的家伙。只要它眼角瞥见了一个分号 `;`，它就会立刻大喊：**“收到！这句话结束了，我马上执行！”**
* **存储过程的矛盾**：存储过程就像是那段“长篇大论”。它内部的 `BEGIN` 和 `END` 之间，包裹着好几句独立的 SQL 语句，而按照语法规定，**内部的每一句独立 SQL 都必须用 `;` 结尾**。

### 🚨 如果不改 DELIMITER，到底会发生什么灾难？

我们来看看如果不加 `DELIMITER //`，只用默认的 `;`，数据库会怎么误解你的代码：

```sql
CREATE PROCEDURE `自动结算`()
BEGIN
    DECLARE total DECIMAL;
    -- 🛑 数据库读到这里，看到了第一个分号！
    -- 它以为你写完了，立刻强行执行上面的半截代码！

```

**数据库的崩溃瞬间：**
数据库看到第一个 `;`，立刻截断代码跑去执行。结果它发现：

* “咦？你前面写了 `CREATE PROCEDURE` 和 `BEGIN`，怎么没有 `END` 就结束了？”
* “语法错误！残缺不全！”
然后它就会当场罢工，给你抛出一大串红色的 Syntax Error（语法错误）。

---

## 第三阶段：深入本质（偷天换日的 `DELIMITER`）

为了解决这个“发送键冲突”，数据库设计者给了你一个修改发送键的特权命令：**`DELIMITER`（定义结束符）**。

当你写下这套标准组合拳时，底层发生的事情如下：

```sql
-- 动作一：修改发送键
DELIMITER //  
-- 机器人的内心 OS：“好的，从现在开始，我只认 // 为执行命令。看到普通的分号 ; 我不管，那是单纯的标点符号。”

CREATE PROCEDURE `自动结算`()
BEGIN
    DECLARE total DECIMAL;       -- 遇到 ;，机器人不执行，继续往下读
    SELECT SUM(price)... ;       -- 遇到 ;，机器人不执行，继续往下读
    INSERT INTO orders... ;      -- 遇到 ;，机器人不执行，继续往下读
END // 
-- 🛑 动作二：完美发送
-- 机器人的内心 OS：“看到 // 了！这是一整块完整的代码，我把它整体打包编译，存进数据库！”

-- 动作三：恢复默认设置
DELIMITER ;
-- 机器人的内心 OS：“好的，改回默认设置，以后看到 ; 我就立刻执行。”

```

### 💡 核心总结

* **`DELIMITER //` 的本质，就是给数据库吃一颗“定心丸”**。告诉它：“待会儿无论在代码里看到多少个分号，都给我憋住别执行，直到看见 `//`，你再把它当成一个完整的整体一口气吞下去。”
* 你不仅可以用 `//`，很多老程序员也喜欢用 **`$$`**，效果是完全一样的（`DELIMITER $$`）。只要这个符号不会在你内部的 SQL 语句中出现，用什么当临时发送键都可以。

没错，存储过程的物理边界，**绝对不是靠 `END` 决定的，而是死死依赖那个毫不起眼的 `DELIMITER`（定界符）**。

我们继续用“从具体到抽象”的方法，深入到数据库的物理架构中，来看看为什么高大上的 `END` 居然靠不住。

## 第一阶段：感性认识（为什么 `END` 靠不住？）

想象你在写一部长篇小说。

如果你跟出版社约定：“只要看到原稿里出现‘结束’这两个字，就代表全书写完了，可以直接拿去印刷。”
这听起来没问题，但如果你在小说的第三章写了一句台词：

> *男主角冷冷地说：“你们的阴谋到此**结束**了！”*

完了！出版社的机器看到“结束”两个字，立刻强行截断，直接把前三章拿去排版印刷，后面的大结局全扔了。

在数据库里，**`END` 就是极其容易引发这种误会的词！**
因为在复杂的存储过程里，`END` 实在是太常见了。你看下面这段代码：

```sql
CREATE PROCEDURE `复杂结账`()
BEGIN
    IF VIP_level = 1 THEN
        SET price = price * 0.8;
    END IF;  -- 🚨 这里有一个 END！

    WHILE count < 10 DO
        SET count = count + 1;
    END WHILE; -- 🚨 这里又有一个 END！
END //       -- 真正的结尾

```

如果系统只看 `END` 来决定是否结束，那么在读到 `END IF;` 的时候，它就以为整个存储过程大结局了，直接截断报错。这就是为什么 `END` 根本承担不起“定界符”的重任。

## 第二阶段：理性认识（揭开底层真相：DELIMITER 到底是在给谁下命令？）

这里有一个极其硬核、甚至很多工作了几年的程序员都不知道的底层真相：

> **`DELIMITER` 这个指令，根本就不是发给“数据库服务器（MySQL Server）”的，而是发给“数据库客户端（比如你用的 Navicat、DataGrip 或者黑乎乎的命令行窗口）”的！**

用唯物主义的架构观来看：

1. **客户端（前端收发发员）**：它的智商很低，它根本不懂什么是 `BEGIN` 什么是 `END`。它的唯一任务，就是**无脑收集你敲击的字符**。收集到什么时候为止？收集到看见“发送键（Delimiter）”为止。然后把收集到的一大坨文本，打包通过网线扔给远端的服务器。
2. **服务器（后台大厨）**：它才是真正懂 SQL 语法的聪明人。它收到包裹拆开后，才会去严谨地核对里面的 `BEGIN` 和 `END` 有没有成双成对。

**因果律推演：**
如果你不改 `DELIMITER //`，用的还是默认的分号 `;`。
你的**客户端（前端收发员）**在读到 `DECLARE total DECIMAL;` 时，看到了分号，它以为你写完了，立刻把这半截残缺的代码打包发给了**服务器（后台大厨）**。
大厨拆开一看：“这写的什么破烂？只有开头没有 `END`？”然后给你抛出一个无情的语法错误。

---

## 💡 终极总结

所以，你的直觉极其精准：

* **`DELIMITER //`** 是物理层面的“打包封箱胶带”，它告诉客户端：“把我用胶带缠起来的这整坨东西，原封不动地发走！”
* **`BEGIN ... END`** 才是逻辑层面的“起承转合”，它告诉服务器：“这里面是一个完整的业务逻辑块，请按顺序执行。”
